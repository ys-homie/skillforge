# 埋点处理

按“需求与属性对比 → 风险文档 → 当前版本开发 → check 文档”执行。纯埋点补齐属于小改动，不自动进入新页面的完整 Plan 流程；若用户只要求分析/check，则输出分析和检查结果，不擅自开发。若涉及新增业务页面或流程，按项目需求开发流程处理该部分。

## 1. 确定需求范围与代码基准

- 读取用户提供的埋点表、说明及当前任务补充要求。使用当前环境可用的文档或表格工具读取；若安装了飞书技能，按资源类型使用 `lark-doc` / `lark-sheets` / `lark-base`，保留链接、工作表、版本、页面、原始行号和读取时间。分页或截断时补全目标范围，不能把未读内容当成不存在。
- 严格按用户指定的版本、页面或行号筛选，例如“V1.5.8 新增 / homepage”或“11–20 条”。共享封装涉及其他页面时检查影响，但不扩大开发范围。
- 读取当前项目 `AGENTS.md`；记录仓库绝对路径、当前分支、HEAD、项目版本配置中的版本/build（Flutter 如 `pubspec.yaml`）、起始 `git status --short` 及相关未提交 diff。当前版本指当前工作区（含已有未提交改动），不能只看 HEAD，也不能照搬旧任务路径或旧分支结论。
- 用户要求版本对比时，记录两端实际 ref/commit；不为分析切换分支或覆盖工作区。只看版本号不足以判断线上包包含哪些修复。
- 需求未给出事件、属性或统计口径时，先查已有定义和当前任务已确认约定；缺少会影响实现的语义再集中询问，先推进不依赖答案的部分。不自行编造事件名、属性名、枚举或业务成功条件。

## 2. 对比已有事件与属性，先输出风险文档

<!-- [项目特定] 填写统一埋点入口、SDK/桥接目录及支持平台。 -->
优先检查项目统一埋点封装、目标页面/状态管理层、共享组件和服务；涉及最终 payload 或跨端差异时继续追踪桥接层及各平台 SDK 实现。须以当前代码核实完整调用链。

每项需求分配稳定编号（优先保留原表行号），逐项确认：

- 事件是否已有封装、真实调用及可达入口；同名不代表同语义，有封装不代表已接入。
- 属性是否出现在当前事件、其他事件、公共/动态属性、用户属性或 `ext` 中；区分“属性 key 已有”“指定事件缺少属性”“属性值/枚举缺失”“类型/语义冲突”“本地未找到”“平台未核实”。
- 对比名称及大小写、类型（STRING/NUMBER/BOOL 等）、单位、枚举、必填性、空值/默认值、取值来源、覆盖顺序与最终上报层级。检查共享参数或 `extra` 合并是否覆盖标准字段。
- 检查同语义异名与同名异义，优先复用已有事件/字段。客户端搜索无结果只能证明本地未找到，不能宣称神策等平台尚未注册；有可用平台字典时再交叉核实。
- 追踪入口 → 展示/操作 → 异步结果 → 上报封装 → 原生/SDK 的实际流程；识别已有埋点是否会与新增调用叠加。

开发前使用 [文档模板](references/report-templates.md) 写出 `analytics-risk.md` 并向负责人提供路径及主要结论。即使没有发现风险，也要保留对比表和未验证边界。

风险要写明具体触发条件、受影响事件/属性/页面、代码证据、影响和处理方案，重点包含实际涉及的：字段类型或枚举改变、旧看板/SQL/漏斗兼容、事件次数变化、重复/漏报、来源参数串页、空值、共享封装影响、双端差异、当前版本缺少组件。不得只有笼统风险清单。

已明确授权的字段对齐直接实施，不新增例行审批。存在无法从需求判断的统计语义冲突时，列出具体差异和建议，仅待确认项暂缓，继续处理确定项。

## 3. 基于当前代码开发

- 优先复用 项目统一埋点入口及现有业务封装，做最小改动。未在需求中要求的事件重命名、删除、类型变更、枚举迁移、去重粒度调整不顺带修改；确需变更时记录兼容影响。
- 不因新增诊断信息随意增加独立事件或把 `ext` 内容提升为顶层属性。遵循当前事件约定，保留历史字段、单位与错误码含义；也不把所有新字段一律塞入 `ext`。
- 明确区分点击意图、提交尝试、成功和失败。点击事件不能擅自变成成功事件；文档要求成功完成才统计的操作应在真实成功分支触发，排除失败回滚、禁用、无效和重复操作。
- 曝光对应实际展示，不在普通 UI 渲染/`build`、列表遍历或轮询中无条件上报。检查 组件卸载重建、Tab/路由切换、前后台恢复和重复打开；按现有或明确要求的口径选择一次展示、会话或业务实体级去重，不自行改为全局只报一次。
- 保留功能按钮节流、异步提交防重和双击手势。Toast/弹窗在实际展示分支记录曝光；关闭按钮、遮罩点击、返回键和滑动关闭按需求区分，不全部误报为点击关闭。
- 共享组件从真实调用方传递 `page_name`、入口和来源；检查所有受影响调用方，不能默认全部写成 `homepage`。动态版本、SKU、来源等值取自真实业务状态，不照抄旧需求常量。
- 埋点不得改变业务返回结果、异常处理或异步顺序，不阻塞主流程。涉及缓存/补发时检查初始化、身份就绪、离线恢复和重试导致的重复事件。
- 关键触发时机、去重边界和兼容处理补齐注释，兼容项目所有目标平台。文档要求的组件在当前代码不存在时，列为未实现及原因，不用相似旧组件冒充，也不擅自新建业务页面。

## 4. Check 并输出检查文档

实施后重新读取最终代码与需求逐项对照；不能只看改动行或搜索字符串存在。纯 check 模式同样检查真实调用与业务路径。

- 覆盖事件名、属性名/值/类型/单位、触发条件和次数、来源透传、失败/取消/重复点击、重复展示、相关平台路径和旧调用兼容。只检查与改动实际有关的边界。
- 运行项目对应的格式化、静态分析和 `git diff --check`。涉及行为的新增/修复按项目要求补 UI、状态管理或业务单元测试（Flutter 如 widget/provider 测试），捕获事件 payload 和次数；不要用源码字符串断言代替行为测试。无法运行时注明原因，并给出可复现的自测步骤和已有证据。
- 临时测试执行后遵循项目 `AGENTS.md` 的保留/清理规则；仅在项目明确要求时清理本次生成的临时测试代码，保留执行命令、结果与日志；不删除原有测试或用户文件。已有测试的修改按当前用户要求处理。
- 运行时验证只使用测试数据和可控上报环境；区分本地捕获、桥接调用、SDK 发送与平台入库，不把其中一个当成完整链路成功。没有真机/平台证据就标注未验证。
- 输出 `analytics-check.md`，每个原始需求编号都有结果和证据。结论为“通过 / 未通过 / 待确认 / 未验证 / 不适用”，不适用须说明依据；存在未完成项时不能宣布全部完成。
- 必须汇总“页面/场景 → `page_name` → 事件 → `module_name` / `pop_name` / `btn_name` / 来源字段（适用时）”，方便负责人查表和联调。
- 交付前复查工作区，区分本次与原有改动；记录最终 HEAD 和相关 diff 摘要/校验值，保证 check 对应可追溯版本。后续代码变化需更新当前 check，保留原有结论与修订记录。

## 事件量异常的额外检查（仅适用时）

区分事件总次数、人数和人均次数，结合平台、build、版本、时间范围与时区分析。先确认目标是事件名还是某事件的属性值；例如弹窗标识可能是 `pop_name` 的值，不能仅按名称搜索事件定义。

对比触发范围、历史数据扫描、状态恢复、组件挂载次数、重试与补发策略。曝光增长不等于业务失败增长；代码推断与线上数据证据分别写清，给出需要补充的筛选条件或时间线，不凭计数直接下故障结论。

## 文档与交付

- 风险文档、check 文档及截图/日志默认保存到当前任务可写的仓库外持久目录；无此目录时用系统临时目录并说明清理风险。已有 Git 忽略目录可沿用。保持路径可点击、证据可回溯，不进入 Git 待提交变更或暂存区。
- 默认输出本地 Markdown；用户要求飞书输出时使用对应技能创建/更新文档。读取需求表不等于获准修改原表，不自行写回验收状态或发消息给其他人。
- 最终回复简述完成与未完成项、关键风险、验证边界，提供两个文档链接和 `page_name` 汇总所在位置。默认不执行 `git add`、`git commit` 或 amend。
